# デプロイ後リグレッション診断ランブック

デプロイ直後にエラーレートが急上昇した場合、コンテナ起動失敗（`Init.Failure`、`Runtime.ExitError` 起動時）が発生している場合、またはCloudFormationスタックの更新後から障害が始まった場合にこのランブックを適用してください。

## 調査手順

**順番通りに**各ステップを実行し、次に進む前に発見事項を記録してください。

### ステップ1 — CloudWatchアラームを確認

`get_active_alarms` を呼び出し、ALARMステートにあるアラームを特定する。
`get_alarm_history` でアラームが発火した時刻を確認し、デプロイ時刻との相関を見る。
デプロイ直後（数分以内）にアラームが発火しているかどうかが重要な証拠になる。

### ステップ2 — Lambda設定とCloudFormationスタックを検査

インシデントに記載されている関数名で `inspect_lambda` を呼び出す。

以下を確認する：
- **タグ `aws:cloudformation:stack-name`**: デプロイされたスタック名を特定する。
- **環境変数**: 接続先URLやフィーチャーフラグの設定値がデプロイで変わっていないか。
- **コードサイズ・レイヤー**: 直近のデプロイで変更されたコンポーネントを特定する。

特定したスタック名で `describe_cfn_stack` を呼び出し、スタックの現在のステータスと最終更新時刻を確認する。
スタックが `UPDATE_ROLLBACK_COMPLETE` や `UPDATE_FAILED` の場合はデプロイ失敗が確定。

次に `get_lambda_recent_errors` を呼び出し、起動時エラー（`Init.Failure`）や設定ミスに起因する例外を確認する。

### ステップ3 — コミュニティナレッジを検索

Stack OverflowとGitHub Issuesで観察したエラーメッセージとフレームワーク名を検索する
（例：`"Lambda Init.Failure container image entrypoint"`）。
デプロイに使用しているフレームワークやランタイムの既知のバグをAWSドキュメントで検索する。

### ステップ4 — 過去のインシデントを確認

`search_past_tickets` を呼び出して、同じスタックや関数で発生した以前のデプロイ障害を探す。
ロールバック手順が記録されている場合はその手順を優先する。

## 確信度レベル

| レベル | 割り当て条件 |
|---|---|
| **high** | CloudFormationスタックが `UPDATE_FAILED` / `ROLLBACK` ステータス、または `Init.Failure` がデプロイ直後のログに存在 |
| **medium** | エラー発生時刻とデプロイ時刻が5分以内に一致し、環境変数や設定の変更が確認される |
| **low** | デプロイとの時系列相関はあるが直接的なエラー証拠がない |

## 主要な診断上の問い

1. 障害はデプロイ完了の何分後に始まったか？
2. 前回の正常なデプロイからどのコンポーネント（コード・設定・依存ライブラリ）が変わったか？
3. ロールバックによって問題が解消するか？
4. デプロイパイプラインにステージング環境での統合テストが含まれていたか？
